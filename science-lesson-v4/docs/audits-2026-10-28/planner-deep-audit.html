Group 1

Quick wins

Small fixes with a clear payoff. Most protect data or remove a daily annoyance.

SmallData safety

Two homeworks for one class on the same day get the same label

Results, "Mark as marked" and the daily results can attach to the wrong homework.

When a homework is set, the planner gives it a label made of the class, the day and a count. The count never goes above 1, because Google Sheets turns the typed date into a calendar date and the comparison then never matches. So the Core and Challenge versions for 10C2 set on the same day, or a quiz and a Seneca link, share one label, and the planner always finds the first one. The rest of the Homework tab already reads the dates the right way; this one spot needs to do the same.

Code.gs setHomework: `n = rows.filter(r => String(r[10]) === setOn)` compares a Date to 'YYYY-MM-DD'. Use hwRows_() (as setLinkHomework_ does). Existing rows with clashing ids may need a one-off relabel in the sheet. The fake sheet in test-homework-quiz.js keeps dates as text, which hid this.

SmallData safety

Tick saves that fail say nothing, and closing too soon can lose them

He trusts "All changes saved"; today that can be untrue for lesson ticks and for the later weeks that slid along.

A save sends the week first, then the ticks, then any later weeks that moved. Only the first part reports a problem. The "you have unsaved changes" warning also stops as soon as the week is sent, so shutting the laptop a second later can drop the ticks. Fix: keep a red "NOT saved" message until all three parts land, retry once by itself, and keep the closing warning on until everything is sent.

Planner.html save(): run('saveLessons') has no .catch and no status; S.recSaved only updates on success. beforeunload checks S.dirty only; add an in-flight counter for saveLessons and saveWeeks.

SmallBehaviour

Homework making blocks behaviour taps; a retried tap can count twice; one bad tap can jam the queue

A double negative can look like a detention, and a stuck queue means later taps never reach the sheet.

  • Making a Google Form holds the app's single lock for up to a minute. A tap from the phone waits 10 seconds, gives up, and drops into the "no signal" queue, and the board stops updating meanwhile. Give behaviour its own lock.
  • If Google saved a tap but the reply was lost, the phone sends it again. Give each tap an ID and let the server ignore a repeat.
  • The queue sends taps in order and stops at the first failure, so a tap that always fails holds back every tap behind it. After three failed tries, set it aside and show it on the connection screen.

Code.gs setHomework/setLinkHomework_ use getScriptLock().tryLock(30000) around buildQuiz_ and Classroom; Behaviour.gs withLock_ uses the same script lock with waitLock(10000). Use LockService.getDocumentLock() for behaviour, or shrink the homework lock to the receipt write. Phone.html log() and flushQueue(); Behaviour.gs logEvent/logMany: skip a row whose (tapTime, class, name, type) already exists in today's rows.

SmallTests

Put the planner tests into the main test command

The project rule is "tests green before any session ends", but the planner's tests are not part of that run.

Five planner test files exist and all pass today. They only run when someone remembers to start them by hand. Adding them to the main run makes every session check the planner too. At the same time, make the fake spreadsheet in the tests behave like the real one with dates, so slips like the homework label one show up.

Add planner/test-logic.js, test-homework-quiz.js, test-mailbox.js, test-ordersheet.js and tests/server.test.js to FIXTURES-style list in test/run.js (or a second step in the npm script). In both mocks, convert appended 'YYYY-MM-DD' strings to Date unless the cell format is '@'.

SmallWorkflow

Show what changed since the last paste, and which version is live at school

Built features sit unused until pasted; the memory notes say "built, not yet pasted" again and again.

Each update means pasting up to ten files into the school's Apps Script editor, with no easy way to tell whether the school copy matches home. Two small helpers: the bundle step lists only the files that changed since the last paste, and the planner and phone show a build date in the corner so a mismatch is obvious. The bundle step should also warn when a file grows near the size where the editor stops saving (one file already failed at about 400 KB; the game file is at 253 KB). Worth a five-minute check: if the school allows Google's own command-line upload tool on his account, pasting could stop altogether. It may be blocked like Drive for Desktop.

bundle.js: store file hashes in dist/.last-paste.json, print the changed list, warn above 300 KB. Code.gs VERSION is still 5; stamp a build date into Planner.html and Phone.html at bundle time. clasp needs the Apps Script API switched on for the school account.

SmallDates

Term dates and Week A/B in one place

A missed copy next September means the phone opens the wrong classes and the planner plans the wrong week.

The term dates live in three copies (the planner's data from home, the behaviour code, and the home class list), and Week A/B is worked out by two separate pieces of code that agree today. After 28 July 2027 every week reads "Week A" until each copy is updated; checked for 6, 13 and 20 September 2027. The behaviour part already reads the planner's timetable, so it can read the terms from there too. The old backup timetable in the behaviour code still lists last year's classes and can go. One test should check that both Week A/B answers match for every week of the year.

Behaviour.gs TERMS, WEEK_A_START, TIMETABLE (7BYA, PSHE-9AB), FORTNIGHTLY. Read data.terms and data.weekAStart via plannerTimetable_-style cache. Agreement test: logic.js weekLetter vs Behaviour.gs weekLetter_ over 2026-09-07..2027-07-26.

SmallHomeworkSaved goal

Homework due shows on the lesson, plus the follow-up ticks

"Collect homework" is one more thing to remember each lesson; the Homework tab already knows every due date.

On the lesson where a homework is due, the card shows "HW due: P1 Energy quiz" and the collect step is ticked in the lesson checklist, which he can untick. The same change adds the two ticks from the saved follow-up goal: "follow-up task here" (after a marked test review) and "key homework returned this lesson". Both go into the build request, so Claude adds the slide. The book page part waits for the CGP index; until then Claude picks the question at home.

logic.js CHECKS (add followUp, keyBack) and buildPrompt; Planner.html render() lesson card flags from S.hwStat by cls + dueOn; default checks.collectHw when a homework is due that day.

SmallOrder sheet

Order sheet as a ready email draft

Every week: download, open email, attach, address, type. This makes it one click, then he reads it and presses Send.

"Email to technicians" makes a Gmail draft on the school account with the Excel file attached and the usual short message. Nothing is sent by itself. Free; it needs one new permission the first time.

Code.gs exportXlsx already builds the blob; add GmailApp.createDraft(to, subject, body, {attachments}). Technicians' addresses as a script property (TECH_EMAILS). Log it in the Log tab the way the download is logged (the Rituals order-sheet check reads that).

SmallSpeed

Saving waits for the home link every time

Each tick or equipment edit also sends the whole planner state home, which adds seconds and up to 6 seconds of retry waits when Google is busy.

Send home at most once every few minutes, or once a night with the 6am results run. Home only needs it before Claude builds lessons.

pushState_ is called from saveWeek, saveWeeks, learnEquipment, saveClassSetting, createLesson, renameAdded. Throttle with a CacheService stamp, and always push from dailyResults and sendRequest.

SmallHomework

Two small homework slips

Each can make a duplicate Form or show the wrong status.

  • The menu's "Homework quizzes" button has no guard against a double click, so two Forms can be made for one quiz. The Homework tab's own button is guarded.
  • Unticking "Mark as marked" on a scheduled homework puts it back to "drafted" instead of "scheduled".

Code.gs makeHomework: wrap in the same lock as setHomework. markHomework(on=false): restore 'scheduled' when postAt is set.

Group 2

Next

Bigger, still high value. The first one is the most serious risk in the app.

MediumData safety

Stop an old planner tab overwriting newer work

This is the one path to real data loss: lesson ticks made at home can vanish without a message.

Every time the ticks are saved, the page sends its complete list and the sheet replaces what it had. If a planner tab stays open on the school computer and saves after he ticked lessons at home, its older list goes back in and the home ticks are gone. Weeks work the same way. Fix in two parts: save only the ticks that changed, and give each save a "version I started from" so the server can say "This page is out of date. Reload" instead of writing over newer work.

Code.gs saveLessons clears the Lessons tab and rewrites it from the client; saveWeek/saveWeeks have no conflict check. Add a saved-at stamp per week row and per record, a server-side merge by cls|key, and a loadAll stamp the client sends back. Test with two simulated tabs.

MediumNorth star

A "Today" panel: the morning brief inside the app

The separate brief was built but never ran and needs a cloud agent; the planner already holds almost everything it would say.

One screen on the laptop, and a "Today" card on the phone: today's lessons in order, the kit and printing, carry-overs from last lesson, homework due and to collect, tests coming up, last homework's weakest questions, and behaviour follow-ups such as detentions and "report to me". It only shows; he decides. Free, and no laptop needs to be on at home.

New view in Planner.html built from S.week, S.hwStat, S.results and behaviourWeek; phone card via one new server call returning today's slots (lessonMcqs already finds today's week). Keep pupil names on the school side only.

MediumSpeed

Faster Homework tab

It gets slower every week, and a slow tab is a tab he stops opening.

Opening it asks the home link for each quiz one at a time (up to 13 trips), then asks Classroom and Forms about the last 60 homeworks, one by one. Fix: fetch all quizzes in one trip, and only check homework that is not yet marked and was due in the last three weeks.

Mailbox.gs: add op 'readMany'. Code.gs homeworkList (serial mailGet_), homeworkStatus (Classroom get + allSubs_ + FormApp.openById per row, 60 rows).

MediumBehaviour

The behaviour log slows down through the year

Taps feel slower each month, and by spring the older lesson cards lose their positive and negative counts.

Every tap reads the last 8,000 rows of the log. At roughly 300 taps a week that ceiling arrives around spring; after it, lesson cards for older weeks and "positives over the last N days" quietly undercount. Fix: read from the bottom only as far as today needs, and move each finished term into an archive tab in the same spreadsheet. The phone's MCQ screen also re-reads the whole 373 KB lesson data on every call; keep a cached copy.

Behaviour.gs readLog_ (LOG_TAIL 8000), today_, positivesOver, behaviourWeek; lessonMcqs parses the Data tab each call (use the CacheService pattern of plannerTimetable_).

MediumSpeed

The planner page gets slower as saved weeks pile up

By summer each change could freeze the page for several seconds on a school computer.

Measured at home with a full year of saved weeks: after one change, moving the later weeks along takes about 1.8 seconds on the home PC, and it runs after every save. The planner works out each class's position by replaying every week since September, many times per click. Fix: remember each week's starting point, and only move later weeks when the change actually affects them.

logic.js progressBefore (replays from lastFilled), cascade (reflowWeek on every later saved week). Memoise progress per monday, invalidated by saves. Add a timing test with 41 weeks.

SmallSaved goalLearning loop

Most-missed questions, across classes

This is the "what did they get wrong" dashboard from the Forms goal, and the data already exists.

The daily results already keep, per class, the percentage for each question, the wrong answers picked most and the mark points missed. A view in the Assessment tab can list the weakest questions over the last few weeks, each with the existing "Put on next lesson's Do Now".

Planner.html Assessment tab from S.results (Results tab rows, class counts only). No new server code.

SmallSaved goalLearning loop

Card votes show on the next lesson

The A/B/C/D votes are saved but go nowhere yet; closing that loop is the north star.

Votes already store the percentage right and the main wrong answer for each question. Show a class's weakest votes on its next lesson card and offer them for the Do Now, just as homework results are.

Read the "MCQ Votes" tab in loadAll_ (class level only), show on the card next to "HW %", feed the Do Now picker request.

SmallSaved goal

Key homework cycle reminders

Key homework should be marked within a week of setting; nothing reminds him today.

The status strip shows "Key homework, 10C2, set 6 days ago, not marked", and the lesson where it comes back gets the "key homework returned" tick from the quick win above. The review section inside a normal lesson is a separate build job for the lesson maker.

logic.js hwStatus: a 'key' row older than 5 days and not marked shows as due to mark. The in-lesson review section needs a builder part (science-lesson), not the planner.

SmallSaved goal

A note for next year on each lesson

What worked and what to change is lost by next September; it was on his own list of planner gaps.

Each lesson already has one saved record keyed by its Drive folder. A short "note for next year" field there will show up whenever that lesson is planned again, for any class, and goes into the build request.

Lessons tab record field `nextYear`; show in topicList and buildPrompt. Key is lessonId (Drive rel), so it survives the class change.

Eyes-free behaviour entry

Logging without looking down keeps his attention on the room.

Draw a pupil's initial with a thumb, then one tap for a positive, two for a negative. Needs a design pass first (what to show when two pupils share letters), then a careful build with the offline queue fixes above in place.

MediumWorkflow

Tomorrow's lessons built before 7pm without asking

"Do my planner requests" still needs him to start Claude at home.

A scheduled Claude session on the home PC could pick up the requests at, say, 5pm. It uses his Claude plan, not a paid API, but the PC must be awake. Respect the 7pm rule: never schedule it later.

A scheduled task firing into a session on the home PC; Remote Control launcher already exists (start-remote-control.cmd).

MediumSaved goal

Open the lesson folder from the planner, and post lessons to Classroom after the day

Fewer trips through Drive folders; pupils get the slides without him uploading.

The home link could look up a lesson's folder and return its address. Check first that the school browser can open his personal Drive. The Classroom post stays a draft he publishes.

Mailbox.gs new op 'folderUrl' by Lessons/rel; classroomDraft_ pattern for materials.

SmallBoard

The board asks the server every second

About 3,600 requests an hour while the board is open; if Google ever slows the app, the board freezes first.

Ask less often when nothing is happening, and quickly while a silence or timer runs. Low risk today, so later.

BoardPage.html poll() via the 1000 ms interval; back off to 3 to 5 s in teaching mode.

Question 4

Phone and laptop

Laptop

  • Weekly jobs hide in the "More" menu: order sheet, calendar, daily results, homework quizzes. A small "This week" strip could show what is sent and what is not (order sheet, calendar, tomorrow's lessons, homework drafted). It shows; it never acts.
  • Errors appear in the small status line and get covered by the next "Saved". Keep any error on screen until he closes it, as the Homework tab already does.
  • Keyboard shortcuts, undo and the drag questions work well. Keep them.
  • The README still describes the old Excel template step; tidy for Claude only.

Phone

  • The behaviour page is solid: it opens from a saved copy with no signal, keeps taps offline and shows errors at the top.
  • Missing: a read-only "Today" card (lessons, kit, homework due). That is the one planner thing he needs mid-day on the phone.
  • Class lists are kept on the phone for offline use. That is fine on his own locked phone; worth knowing if the phone is lost.
  • The connection dot turns amber whenever the board is closed, so amber often means nothing is wrong. A separate board indicator would make amber mean "taps waiting".
Question 5

Test gaps

  • Not run with the main test command. Five planner test files only run by hand.
  • The fake spreadsheet is too kind. It keeps dates as text; real Sheets turns them into dates. That hid the homework label clash.
  • No test for two open copies saving. The overwrite risk has no check at all.
  • No test that failed saves are reported. The planner page itself is only checked by screenshots.
  • No check that both Week A/B answers agree, and nothing tests next September's rollover.
  • No speed test. A year of saved weeks is never timed.
  • Offline taps: no test for a repeated tap or a tap that always fails. The phone simulations need a browser tool that is installed at home.
Rules check

Against the standing rules

One rule question for Patryk: the order sheet download makes a temporary Google Sheet and then puts it in the bin. It only bins its own temporary copy, but the standing rule is "never delete on Drive". Choose: keep it as it is, or leave the temporary copies in one "Planner temporary" folder that he empties himself.

  • Drive writes: the planner creates quiz Forms in one folder, lesson folders he asks for, and the Planner Sync files. All creates; nothing renamed or moved apart from the point above.
  • Paid API: nothing in the top 10 needs one. Only automatic marking of written answers would, and it is listed as an idea, not a plan.
  • Pupil data: names stay in the school spreadsheet and Forms. What goes home is class-level numbers, and the tests check that. Keep it that way for the Today panel and the votes.
  • Tools that decide for him: every suggestion here shows information or prepares a draft. Nothing sends, posts or re-teaches by itself.
